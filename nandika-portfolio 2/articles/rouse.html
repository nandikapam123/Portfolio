RouseVortex: Localization and Path Following for an FTC Robot

Pose model, calibration protocol, controller rules, and a verification matrix with targets set in advance.

Source repository ↗ Requirements stated; results pending

Scope

RouseVortex is the autonomous software for an FTC robot (repository). It has three layers: a pose estimator (x, y, θ), a path follower, and feedback controllers. This entry states what each layer must satisfy and how I check it. Parameter values and measured results belong with the repository and are not asserted here.

Requirements and how each is verified

Targets are fixed before testing, so a result cannot be quietly reinterpreted afterwards.

Pose model

Odometry gives a body-frame displacement over each loop. Writing the robot-frame translation as (Δxr, Δyr) and heading change Δθ, the field-frame update is the exact arc (exponential-map) form: Δp = R(θ) · [ (sinΔθ)/Δθ , −(1−cosΔθ)/Δθ ; (1−cosΔθ)/Δθ , (sinΔθ)/Δθ ] · (Δxr, Δyr)ᵀ, with the matrix tending to identity as Δθ → 0. Using only Δs·(cosθ, sinθ) assumes the robot did not turn during the step. The figure shows what that costs on a 24 in radius quarter turn.

The consequence is practical: a first-order update needs a loop fast enough that Δθ per step stays small, while the arc form removes that dependence. Residual error then comes from the sensors, not the arithmetic.

Calibration protocol

Systematic odometry errors, chiefly unequal wheel diameters and an uncertain effective track width, dominate over random noise in dead reckoning. Borenstein and Feng’s UMBmark test isolates them by driving a square both clockwise and counter-clockwise: the two error clusters separate the two systematic error types, which random scatter alone cannot do. I use the same structure: record the commanded and measured end pose for each run, compute the centroid of each cluster, and update the scale and track-width constants only from the cluster offsets. Each change is logged with its before and after values.

Controller rules and self-tests

The controller design rules are: derivative acts on the measurement, not the error (no kick on a setpoint step); the integral stops accumulating while the output is clamped (anti-windup, see the Control Systems Notebook); elapsed time is guarded against zero and outliers; and heading error is wrapped into (−π, π] so the robot takes the short way round. These tests run against a reference implementation of those rules in this page, and the repository version should pass the same cases.
